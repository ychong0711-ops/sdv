2. MCU 펌웨어 빌드 및 플래시

1 빌드 (이미 검증 완료)

# Zephyr 환경 (west + SDK) 준비 후, 프로젝트 루트에서
west build -b arduino_uno_q MCU

# 성공 출력 예시 (실측값)
# Memory region         Used Size  Region Size  %age Used
#            FLASH:       96240 B         2 MB      4.59%
#              RAM:       27296 B       768 KB      3.47%
# Generating files from .../zephyr.elf for board: arduino_uno_q/stm32u585xx

2 플래시

# MCU 디버그 포트 연결 상태에서
west flash

# (대체) DFU/직접 기록이 필요한 경우
west flash -r dfu-util
⚠️ 플래시 전 확인 USB-C 케이블이 MCU 디버그/플래시 포트에 연결됐는지 확인하세요. UNO Q에서 MPU 포트와 MCU 포트는 별도입니다. west flash 실패 시 nrfjprog/STM32CubeProgrammer 대체 도구를 확인하세요.

4. UART 터널 검증 (MPU → MCU)

MPU(Debian Linux)에서 Python 클라이언트가 SOME/IP 패킷을 LPUART1로 전송하면, MCU가 수신해 CAN으로 보냅니다.

1 MPU 셸에서 전송 테스트

# MPU 리눅스 셸에서 (프로젝트 마운트 위치 기준)
python3 mpu/ai/trigger_test.py --transport uart --uart-port /dev/ttyS0 --level 85

2 MCU 시리얼 콘솔에서 수신 확인

[00:00:05.123] <inf> someip_service: SOME/IP RX: drowsiness=85%
[00:00:05.124] <inf> can_gateway: CAN TX: ID=0x18FF01F4 DLC=8 Data=55 AA 01 55 00 00 CRC CNT

3 패킷 형식 확인 (의미)

바이트값의미
0-112 34Service ID (0x1234)
2-380 01Event ID (NotifyDrowsiness)
4-700 00 00 09Length (= payload 1 + 8)
8-1100 01 00 01Client ID / Session ID
12-1501 01 02 00Proto/Interface/Type(Notify)/Return
1655drowsiness level (85% = 0x55)
💡 UART로 Wireshark 캡처는? UART는 raw 바이트 스트림이라 pcap으로 직접 캡처되지 않습니다. 대신 serial->udp 중계기 (예: socat)로 감싸면 PC의 Wireshark에서 같은 패킷을 분석할 수 있습니다:
socat -d -d PTY,link=/tmp/vcom,raw /dev/ttyS0,b115200

5. CAN-FD 실물 검증

1 CAN 트랜시버 연결 (없으면 루프백)

  • MCU FDCAN1 핀 → CAN 트랜시버 → CAN 버스 (H/L)
  • 트랜시버가 없으면 내부 루프백으로 자체 수신 확인 가능 (MCU가 자기 프레임을 받음)

2 MCU에서 CAN TX 확인

MCU 코드는 졸음 레벨 수신 시 다음 CAN-FD 프레임을 전송합니다:

ID       : 0x18FF01F4 (J1939 확장 프레임)
DLC      : 8
Data[0]  : 0x55  (프로토콜 태그)
Data[1]  : 0xAA  (마커)
Data[2]  : 0x01  (경고 타입)
Data[3]  : level (0-100, 졸음 정도)
Data[4]  : 0x00  (예약)
Data[5]  : 0x00  (예약)
Data[6]  : CRC8  (E2E 보호, 다항식 0x1D init 0xFF)
Data[7]  : Alive Counter (0-15 순환)

3 PC에서 CAN 수신 확인 (어댑터 있을 때)

# Linux + CANable/PCAN 어댑터
sudo ip link set can0 type can bitrate 500000 dbitrate 2000000 fd on
sudo ip link set can0 up
candump can0 -L   # 출력: 18FF01F4 [8] 55 AA 01 55 00 00 XX XX
💡 CRC8 검증 PC에서 수신한 프레임의 CRC8은 MCU의 e2e_crc8과 동일 규칙(다항식 0x1D, init 0xFF, final XOR 0xFF)으로 계산됩니다. Python mpu.someip.protocol.crc8과 유닛 테스트로 교차 검증된 값입니다 — pytest mpu/tests/ 5개 모두 통과 상태.

6. Safe State 실물 검증 (핵심!)

이 프로젝트의 차별점인 ISO 26262 Safe State를 실물에서 검증합니다.

1 정상 상태 확인

MPU가 50ms 주기로 Heartbeat(0x8002)를 보내면 MCU의 Watchdog이 계속 리셋됩니다. 이때는 CAN 경고 프레임이 없고 LED가 정상 상태입니다.

2 실패 주입 (Fail Injection)

# MPU에서 heartbeat 프로세스 강제 종료
pkill -f drowsiness.py
# 또는 UART 케이블 분리

3 Safe State 진입 확인 (100ms 내)

동작기대 결과판정
CAN 경고 프레임level=0xFF 강제 경고 프레임 전송candump에서 확인
LED 점멸빠른 토글 (Safe State 표시)육안/오실로스코프
Watchdog리셋 없이 Safe State 유지시리얼 로그 연속 출력

4 복구 확인

# MPU에서 heartbeat 재개
python3 mpu/ai/drowsiness.py --transport uart --uart-port /dev/ttyS0

50ms 이내 heartbeat가 다시 오면 MCU가 Safe State를 해제하고 NORMAL로 복귀합니다.

⚠️ 안전 동작 원리 Safe State에서는 리셋하지 않고 Watchdog를 의도적으로 계속 먹여 안전 상태를 유지합니다. (리셋하면 무한 재부팅 루프에 빠질 수 있음) 이 설계 결정을 면접에서 설명할 수 있어야 합니다.

7. 전체 시나리오 (E2E)

졸음 감지 → CAN 경고까지 전체 흐름

[MPU] 카메라 프레임 ──TFLite──► drowsiness=85%
  │
  ▼  SOME/IP Notify (0x8001) 24B
[UART LPUART1 115200]  또는  [UDP 30490]
  │
  ▼
[MCU] someip_service 파싱 (CRC/길이 검증)
  │
  ▼
[MCU] can_gateway: CAN-FD TX 0x18FF01F4 [55 AA 01 55 00 00 CRC CNT]
  │
  ▼
[CAN 버스] ──► 계기판/디스플레이 경고

[병행] MPU Heartbeat (0x8002) 50ms ──► MCU Watchdog 유지
[실패] 100ms 미수신 ──► Safe State: 경고 프레임 + LED 점멸

검증 체크리스트

8. 문제 해결 (FAQ)

문제원인해결
west flash 실패 디버그 포트 미연결 / 드라이버 MCU 포트 확인, lsusb로 장치 인식 확인
MPU /dev/ttyS0 없음 LPUART1 노드/권한 dmesg | grep tty, sudo chmod 666 /dev/ttyS0
MCU가 UART 메시지 수신 안 함 Kconfig에서 UART 전송 미활성 MCU/Kconfig의 SOMEIP_TRANSPORT_UART=y로 빌드
CAN 프레임 안 나감 트랜시버 전원/종단 저항 CAN_H/CAN_L 종단 120Ω, 전원 확인
Safe State가 바로 진입함 heartbeat 전송 중단 MPU에서 drowsiness.py 실행 상태 확인 (50ms 주기)
시리얼이 깨져 보임 baudrate 불일치 115200 8N1 확인 (UART 터널 기본값)
💡 최종 조언 실물 검증은 1→6 체크리스트를 순서대로 진행하세요. 2(UART)가 안 되면 3(CAN)은 볼 수 없습니다. 각 단계의 로그/사진을 남기면 면접 증거 자료가 됩니다.
