1. 왜 Yocto인가?

Phase 1은 Debian + Docker로 1분 만에 SOME/IP 프로토타입을 증명했습니다. 하지만 독일 자동차 산업이 요구하는 것은 프로덕션급 빌드 시스템입니다.

구분Debian (Phase 1)Yocto (Phase 2)
빌드 시간1분1-3시간 (sstate 이후 10분)
재현 가능성낮음매우 높음 (정확한 버전 고정)
라이선스 관리수동자동 (license manifest)
이미지 크기큼 (범용 패키지)최적화 가능 (베어메탈까지)
지원 기간5년Kirkstone 10년 LTS
면접 가치프로토타이핑 속도프로덕션 엔지니어링
💡 면접 답변 포인트 "Phase 1에서 Debian으로 SOME/IP를 6주 만에 증명했습니다. 프로덕션 적합성을 위해 Yocto Kirkstone LTS로 이식 중입니다. sdv-hpc-image는 Docker + vsomeip + AI를 포함한 Adaptive HPC 이미지입니다."

2. 요구사항 및 준비물

  • Docker (20.10+): Yocto 빌드 호스트가 컨테이너로 제공됨
  • 디스크 여유 공간: 최소 50GB (빌드 중 소스 다운로드 + tmp 폴더)
  • RAM: 8GB 이상 권장 (bitbake는 병렬 태스크 실행)
  • CPU: 4코어 이상 (빌드 시간에 직접 영향)
  • 인터넷: 최초 빌드 시 소스 다운로드 필요 (1-2GB)
⚠️ 빌드 시간 안내 최초 빌드는 소스 다운로드 + 컴파일로 1~3시간이 소요됩니다. sstate-cache가 생성된 이후부터는 10분 내외입니다. CI에서는 시간 문제로 Yocto 빌드를 생략하는 것도 전략입니다.

3. 프로젝트 구조 (yocto/ 폴더)

yocto/
├── Dockerfile.yocto              # Ubuntu 22.04 + Yocto 빌드 의존성 + poky kirkstone
├── kas.yml                       # kas 빌드 (선택, 없이도 가능)
├── meta-sdv/                     # ★ 커스텀 레이어 (GitHub의 핵심)
│   ├── conf/layer.conf
│   ├── recipes-core/images/
│   │   └── sdv-hpc-image.bb      # HPC 이미지 (Docker + vsomeip + AI + CAN)
│   ├── recipes-support/vsomeip/
│   │   ├── vsomeip_3.4.10.bb     # SOME/IP 스택 (AUTOSAR Adaptive)
│   │   └── files/vsomeip.json, vsomeip.service
│   └── recipes-app/sdv-mpu/
│       ├── sdv-mpu_1.0.bb        # AI 앱 패키징 (systemd)
│       └── files/drowsiness.py, sdv-mpu.service
├── build/conf/
│   ├── bblayers.conf.sample
│   └── local.conf.sample
└── scripts/
    ├── build-yocto.sh            # 원클릭 빌드 (Docker + bitbake)
    └── entrypoint-yocto.sh

각 레시피의 역할

레시피역할핵심 내용
sdv-hpc-image.bb 전체 시스템 이미지 Docker, vsomeip, sdv-mpu, can-utils, tshark, gdb 포함
vsomeip_3.4.10.bb SOME/IP 스택 COVESA vsomeip v3.4.10, boost + dlt-daemon 의존, systemd 서비스
sdv-mpu_1.0.bb AI 앱 패키징 drowsiness.py + trigger_test.py, Python/TFLite, systemd 자동 실행

4. 방법 A: 원클릭 스크립트 (추천)

가장 간단한 방법입니다. 프로젝트 루트에서 한 번만 실행하면 됩니다.

1 스크립트 실행

# 프로젝트 루트에서
./yocto/scripts/build-yocto.sh

2 스크립트가 하는 일

  1. Yocto Docker 이미지 빌드 (최초 1회, 5-10분) — 이미 있으면 스킵
  2. 빌드 디렉토리 준비: yocto/build/sstate-cache, downloads
  3. 컨테이너 실행 + source poky/oe-init-build-env build
  4. MACHINE=qemuarm64 bitbake sdv-hpc-image 실행 (최초 1-3시간)
💡 2회차부터는? sstate-cache가 캐시되므로 10분 내외로 빌드가 끝납니다. 이것이 Yocto의 재현 가능성 강점입니다.

5. 방법 B: Docker 직접 실행 (수동)

스크립트 없이 Docker 명령으로 직접 제어하는 방법입니다.

1 빌드 호스트 이미지 빌드

docker build -f yocto/Dockerfile.yocto -t sdv-yocto:4.0 yocto/

2 컨테이너 실행 (meta-sdv + 빌드 캐시 마운트)

docker run --rm -it \
  -v $(pwd)/yocto/meta-sdv:/home/yocto/yocto/meta-sdv:ro \
  -v $(pwd)/yocto/build:/home/yocto/yocto/build \
  sdv-yocto:4.0 bash

3 컨테이너 내부에서 빌드

# 컨테이너 내부
source poky/oe-init-build-env build
MACHINE=qemuarm64 bitbake sdv-hpc-image
⚠️ 마운트 포인트 meta-sdv는 :ro(읽기 전용)로 마운트됩니다. 레시피 수정은 호스트에서 편집하고 재빌드하세요.

6. 방법 C: kas (CI용 고급)

kas는 Yocto 빌드를 선언적으로 자동화하는 도구입니다. CI 파이프라인에서 유용합니다.

pip install kas
kas build yocto/kas.yml

kas.yml이 관리하는 것:

  • poky (kirkstone 브랜치) + meta-openembedded + meta-sdv 레이어 조합
  • 머신: qemuarm64, 배포판: poky
  • 이미지에 docker-moby, docker-compose, vsomeip, sdv-mpu 포함

7. 빌드 산출물 확인

ls -lh yocto/build/tmp/deploy/images/qemuarm64/
# sdv-hpc-image-qemuarm64.wic.xz  ← SD 카드 플래시용
# sdv-hpc-image-qemuarm64.tar.bz2 ← 아카이브
# sdv-hpc-image-qemuarm64.wic.bmap
파일 확장자용도
.wic / .wic.xzSD/eMMC 플래시 이미지 (dd로 기록)
.wic.bmapbmaptool용 매핑 (빠른 기록)
.tar.bz2루트 파일시스템 아카이브
🔴 현재 상태 안내 이 프로젝트의 Yocto 레시피는 작성 완료 + SRCREV 검증 완료 상태이며, 첫 빌드 성공은 검증 대기입니다. 이 가이드를 따라 빌드를 완료하고, 성공 스크린샷을 yocto/README_YOCTO.md에 기록하세요.

8. QEMU로 테스트 (UNO Q 없이)

빌드가 완료되면 PC에서 가상 머신으로 부팅해 검증할 수 있습니다. UNO Q의 QRB2210(Cortex-A53)은 qemuarm64로 에뮬레이션됩니다.

cd yocto/build
runqemu qemuarm64 sdv-hpc-image nographic

QEMU 부팅 후 내부에서 확인할 것:

systemctl status vsomeipd      # SOME/IP 데몬 상태
systemctl status sdv-mpu       # AI 앱 상태
journalctl -u sdv-mpu -f       # AI 로그 실시간
tshark -i eth0 -f "udp port 30490"  # SOME/IP 패킷 캡처

9. 실제 보드에 플래시 (선택)

UNO Q의 QRB2210은 커스텀 BSP가 필요하므로, 실습용으로 Raspberry Pi 4로 대체 검증하는 방법을 제공합니다.

# Raspberry Pi 4 타겟으로 빌드
MACHINE=raspberrypi4-64 bitbake sdv-hpc-image

# SD 카드에 플래시 (/dev/sdX는 SD 카드 경로로 교체)
sudo dd if=tmp/deploy/images/raspberrypi4-64/sdv-hpc-image-raspberrypi4-64.wic of=/dev/sdX bs=4M
💡 UNO Q 실제 플래시 UNO Q QRB2210에 플래시하려면 Qualcomm BSP(meta-qcom) 레이어 추가가 필요합니다. 고급 과정이며, Phase 2 후반 목표입니다.

10. 문제 해결 (FAQ)

문제원인해결
bitbake: command not found 빌드 환경 초기화 안 됨 source poky/oe-init-build-env build 먼저 실행
vsomeip: fatal error: boost/log/trivial.hpp: No such file boost-dev 의존성 누락 DEPENDS = "boost dlt-daemon" 확인 (레시피에 포함됨)
빌드 중간에 소스 다운로드 실패 네트워크 문제 / 특정 미러 차단 build/downloads 폴더 캐시 유지, 재실행 시 이어짐
디스크 공간 부족 tmp 폴더 대형화 최소 50GB 확보, bitbake -c cleanall로 정리
Docker 마운트 후 레시피 안 보임 bblayers.conf에 meta-sdv 미추가 entrypoint-yocto.sh가 자동 추가. 수동 시: BBLAYERS += " ${TOPDIR}/../meta-sdv "
빌드에 root로 실행 금지 오류 Yocto 정책 (root 빌드 불가) Dockerfile.yocto가 yocto 사용자로 전환함 (자동 처리)

상세 트러블슈팅은 yocto/TROUBLESHOOTING.md 참고.

11. 면접 활용 전략

Q: "Yocto 경험이 있나요?"

A: "Kirkstone LTS 기반 커스텀 레이어(meta-sdv)를 만들었습니다. vsomeip와 AI 앱을 레시피로 패키징하고, systemd로 서비스 관리하도록 이미지를 구성했습니다. MACHINE을 qemuarm64로 설정해 PC에서 QEMU 검증까지 진행했습니다."

Q: "왜 Debian 대신 Yocto인가요?"

A: "Debian은 프로토타이핑에 탁월하지만, 프로덕션에서는 라이선스 관리와 재현 가능성이 중요합니다. Yocto는 빌드가 완전히 결정론적이고, 라이선스 manifest를 자동 생성하며, 10년 LTS를 제공합니다. 독일 자동차사가 선호하는 방식입니다."

Q: "CI에 Yocto 빌드를 왜 안 넣었나요?"

A: "초기 빌드가 3시간이라 CI 대기열에 부담이 됩니다. 그래서 CI는 Phase 1(Debian/Docker)만 자동화하고, Yocto는 로컬에서 sstate-cache로 빌드했습니다. 브랜치별 분리 실행도 준비되어 있습니다."

면접에서 보여줄 증거

  1. GitHub: yocto/meta-sdv/ 폴더 + sdv-hpc-image.bb + vsomeip_3.4.10.bb 레시피
  2. 빌드 스크린샷: bitbake sdv-hpc-image 성공 로그 + ls -lh tmp/deploy/images/
  3. QEMU 시연: runqemu로 부팅 후 systemctl status sdv-mpu 확인
  4. 전문 용어: layer, recipe, bitbake, sstate-cache, MACHINE, IMAGE_INSTALL, WIC
💡 핵심 요약 Yocto는 "코드"가 아니라 "빌드 시스템"을 다루는 역량입니다. 레시피 문법(bb), 레이어 구조, bitbake 태스크 개념을 화이트보드에 그릴 수 있으면 가장 강력한 인상을 남깁니다.
